FN Connect与Cloudflare Zero Trust：一次关于家庭服务器架构的探索与思考

发表于2026-07-23|更新于2026-07-23|折腾日记
|阅读量:

前言

很多人在刚开始折腾 NAS 时，都会遇到一个经典问题：

到底该使用官方提供的 FN Connect，还是 Cloudflare Tunnel？

网上的文章五花八门，众说纷纭。有人极力推崇 FN Connect，因为它可以直接通过 remote-xxxx.fnos.net:端口 访问 Docker 容器；也有人认为 Cloudflare Tunnel 才是最终解决方案，因为它提供了更强大的 Zero Trust 安全能力。

作为一个喜欢刨根问底的人，我决定：：：自己做一次实验。：：

与其相信网上各种帖子，不如亲手验证。毕竟，技术选择从来不是简单的”谁更好”的问题，而是”谁更适合我”的问题。

本文不仅会完整记录整个实验过程，也会深入分析飞牛 FN Connect 的底层技术原理，并最终给出我自己的家庭网络架构设计。更重要的是，我将分享一个核心设计理念：：：存储和计算分离：：。希望通过我的探索过程，能给同样在折腾 Homelab 的你一些启发。

第一章：我的家庭设备清单

在深入技术细节之前，先介绍一下我的硬件配置。理解这些设备的分工，对于后续的架构设计至关重要。

整体网络拓扑

先看一张简化的网络拓扑图：

设备一：飞牛 NAS（网心云 OEC）

硬件配置：

  • CPU: ARM 架构（具体型号为网心云定制芯片）
  • RAM: 4GB DDR4
  • 存储: 2TB 机械硬盘
  • 网络: 千兆网口
  • 功耗: 约 5-8W（低功耗设计）

主要职责：

  • 照片备份 ：通过飞牛相册应用，自动备份手机照片
  • 文件存储 ：作为家庭文件中心，存储文档、视频等
  • 离线下载 ：运行迅雷下载、Aria2 等下载工具
  • 媒体服务 ：通过 Emby/Jellyfin 提供家庭影院服务

为什么选择它做存储中心？

这款设备的最大优势是是是低功耗 + 官方生态 + 专用存储系统是是。网心云 OEC 改装飞牛系统后，能够无缝使用飞牛官方提供的 FN Connect、相册同步等功能，非常适合作为”存储型设备”使用。

更重要的是，飞牛 NAS 的 4GB 内存虽然理论上可以运行 Docker，但更适合运行轻量级的存储和媒体服务。飞牛系统本身就是为存储优化的专用系统，在文件管理、照片备份等方面有着天然优势。

设备二：Mac mini M4

硬件配置：

  • CPU: Apple M4 芯片（8核心）
  • RAM: 16GB 统一内存
  • 存储: 256GB SSD
  • 网络: 千兆网口 + Wi-Fi 6
  • 功耗: 约 6-15W（根据负载动态调整）

主要职责：

  • Docker 主机 ：运行各类容器化服务
  • AI 推理 ：运行 OpenWebUI、Sub-Store、ComfyUI 等本地 AI 应用
  • 博客服务 ：运行 Hexo 静态博客
  • Git 服务 ：运行 Gitea 自托管 Git 服务
  • 开发环境 ：提供完整的开发工具链

为什么让它做服务器？

Mac mini M4 作为主服务器有几个关键优势：

  1. 性能强劲 ：M4 芯片的性能远超 ARM 架构的 NAS，可以流畅运行 10+ 个容器
  2. 内存充足 ：16GB 统一内存相比 NAS 的 4GB，提供了更大的容器容量空间
  3. 稳定可靠 ：macOS 系统稳定性高，长期运行不重启
  4. 功耗合理 ：虽然比 NAS 高，但相比传统服务器仍然低功耗
  5. 开发友好 ：可以直接作为开发环境，编写代码、测试服务

为什么这样分工？——存储和计算分离

很多新手会问：：：为什么不直接在 NAS 上跑 Docker？：：

答案是：：：存储和计算，本就是两件不同的事情。：：

让我们从几个维度深入分析：

内存限制分析

飞牛 NAS 的 4GB 内存虽然理论上可以运行 Docker，但当你同时跑多个容器时，内存很快就会捉襟见肘。

一个典型的服务组合内存占用：

看起来还剩 2.3GB？别忘了：

  • NAS 系统本身需要约 800MB
  • 文件系统缓存需要内存
  • 飞牛相册等官方服务需要内存
  • 突发流量时容器内存会增长

结果就是：内存长期处于高压状态，系统响应变慢，甚至可能触发 OOM Killer。

性能瓶颈分析

ARM 架构的定制芯片性能有限，当同时运行多个容器时：

  • 数据库查询变慢
  • Web 服务响应延迟
  • 容器启动时间长
  • AI 推理性能不足

相比之下，M4 芯片的性能优势明显：

  • 单核性能强劲，适合单线程服务
  • 统一内存架构，数据访问高效
  • 神经引擎加速 AI 推理

稳定性风险

NAS 的核心职责是”存储”，如果因为 Docker 容器占用过多资源导致：

  • 文件传输速度下降
  • 照片同步失败
  • 系统崩溃导致数据丢失

这个风险太高了。

架构设计的核心原则：

存储型设备专注于存储，计算型设备专注于计算。

这种分离不仅性能更好，也更便于后续扩展和维护。

第二章：深入理解 FN Connect

在介绍实验之前，我们需要先搞清楚：：：FN Connect 到底是什么？：：

常见误解

很多人第一次接触 FN Connect 时，会误以为它是一种 DDNS（动态域名解析） 服务。

但实际上，FN Connect 和 DDNS 完全不是一回事：

特性 DDNS FN Connect
工作原理 解析域名到公网IP 反向代理 + 会话管理
是否需要公网IP 是 否
端口暴露 需要开放端口 不需要
安全性 依赖防火墙 内置身份验证

FN Connect 的真正身份

从技术角度看，FN Connect 更像以下几种技术：

  1. Synology QuickConnect ：群晖官方的远程访问方案
  2. Tailscale Funnel ：基于 WireGuard 的内网穿透服务
  3. Ngrok ：反向代理工具

它们的核心共同点是：：：不需要公网 IP，不需要端口映射，通过云服务商的中转服务器实现内网穿透。：：

技术架构示意图

让我们通过一张图来理解 FN Connect 的工作原理：

关键点说明：

  1. FN Connect Agent ：运行在 NAS 上的客户端程序，负责与云端 Gateway 建立长连接
  2. Application Gateway ：云端的反向代理服务器，负责 URL 路由、身份验证、证书管理
  3. 加密隧道 ：所有流量通过 TLS 加密传输，无需担心中间人攻击

和 Cloudflare Tunnel 的对比

既然提到了 Cloudflare Tunnel，我们提前对比一下两者的核心区别：

特性 FN Connect Cloudflare Tunnel
底层协议 自研协议 Argo Tunnel (HTTP/2)
身份验证 飞牛账号 Session Zero Trust (多种策略)
自定义域名 不支持 完全支持
WAF 防护 无 内置 Cloudflare WAF
CDN 加速 无 全球 CDN 节点
适用场景 官方生态一键访问 自建服务、高级安全需求

后续章节我们会深入对比，这里先有个大致了解。

验证 FN Connect 的基础远程访问功能。

实验步骤：

实验三：直接端口访问测试（关键实验）

实验目的：

验证是否可以通过 remote-xxx.fnos.net:端口 直接访问 Docker 容器。

实验步骤：

  1. 保持实验一的 Nginx 容器运行
  2. 在浏览器中访问：https://remote-xxxx.fnos.net:9999

实验结果：

❌ 访问失败 ，浏览器提示连接超时。

为了深入分析，我查看了浏览器开发者工具中的网络请求：

分析：

这个实验揭示了一个重要事实：：：FN Connect 并不是简单的端口转发（Port Forward）：：。

如果是传统的端口转发，理论上 remote-xxx.fnos.net:9999 应该被映射到 NAS 的 内网IP:9999。但实际结果是连接超时，说明 FN Connect 的云端 Gateway 并没有监听 9999 端口。

这初步验证了我的猜想：FN Connect 更像是 Application Gateway（应用网关） ，而不是端口转发器。

更重要的是，这个实验揭示了 FN Connect 的定位问题：

如果你的服务需要通过特定端口访问（比如 OpenWebUI 的 8080 端口、Gitea 的 3000 端口），FN Connect 并不能直接支持。它只能通过飞牛官方的”一键发布”功能，动态生成容器专属 URL。

这种方式对于官方生态（飞牛相册、文件管理）很友好，但对于自建服务来说，缺乏灵活性。

实验四：飞牛 Docker 管理界面访问

实验目的：

验证飞牛官方的 Docker 管理界面如何工作。

实验步骤：

  1. 通过 FN Connect 登录飞牛 NAS 远程桌面
  2. 点击左侧菜单的”容器管理”
  3. 找到运行中的 Nginx 容器，点击容器名称

实验结果：

浏览器地址栏自动跳转到：

✅ 成功访问 Nginx 容器的详情页面。

关键发现：

注意到 URL 的结构变化了吗？

  • 原来：remote-xxxx.fnos.net
  • 现在：2585d28675ee-0.remote-xxxx.xxxx.net

这个 URL 中的 2585d28675ee 正是 Nginx 容器的 ID！

这进一步证明了：：：FN Connect 的 Application Gateway 会动态生成每个容器的专属 URL：：，而不是简单的端口映射。

实验五：跨浏览器访问测试（最精彩的实验）

实验目的：

验证 FN Connect 的 Session 管理机制。

实验步骤：

  1. 在 Chrome 浏览器中，复制实验四生成的容器 URL：
    https://2585d28675ee-0.remote-xxxx.xxxx.net
  2. 在同一浏览器的其他标签页中打开该 URL

实验结果：

✅ 成功访问 ，可以正常查看容器详情。

  1. 在 Edge 浏览器中打开该 URL（未登录飞牛账号）

实验结果：

❌ 访问失败 ，页面提示：

  1. 在手机浏览器中打开该 URL（未登录）

实验结果：

❌ 访问失败 ，提示同样错误。

关键分析：

这个实验揭示了 FN Connect 的安全机制：

  1. Session 绑定 ：每个访问请求都需要验证飞牛账号的登录状态
  2. Cookie/Token 验证 ：Gateway 会检查请求中是否包含有效的身份凭证
  3. 容器级访问控制 ：即使通过了身份验证，也只能访问自己有权限的容器

为什么 Chrome 可以，Edge/手机不行？

因为在 Chrome 中，我已经登录了飞牛账号，浏览器保存了有效的 Session Cookie。而 Edge 和手机浏览器中没有这个 Cookie，所以被 Gateway 拒绝访问。

这种机制和 Cloudflare Zero Trust 的 Access Policy 非常相似，都是基于身份的访问控制，但实现方式不同：

  • FN Connect ：依赖飞牛账号 Session，类似”单点登录”
  • Cloudflare Zero Trust ：支持邮箱验证、GitHub OAuth、一次性密码等多种策略

实验目的：

验证在飞牛 NAS 上运行服务的性能表现。

实验步骤：

  1. 在飞牛 NAS 上部署 OpenWebUI（AI 对话界面）：
  1. 通过本地访问：http://192.168.1.100:8080

实验结果：

⚠️ 部分成功 ，但性能受限。

当 OpenWebUI 处理 AI 对话请求时，我观察到：

  • 响应时间明显变慢
  • 系统内存占用快速上升
  • 其他 NAS 服务（如文件传输）受到影响

分析：

这个实验进一步验证了”存储和计算分离”的必要性。飞牛 NAS 的 4GB 内存虽然可以运行服务，但：

  • AI 推理需要大量内存
  • 多个服务同时运行会争抢资源
  • 影响存储服务的稳定性

更好的方案：

将 OpenWebUI 部署到 Mac mini M4，利用 M4 芯片的性能和 16GB 内存，可以获得更好的性能和稳定性。

第四章：FN Connect 技术原理深度分析

经过前面的一系列实验，我们可以总结出 FN Connect 的核心技术架构。

核心结论：Application Gateway，而非 Port Forward

让我们先明确两者的区别：

Port Forward（端口转发）

传统端口转发的工作流程：

关键特点：

  • 每个服务需要一个公网端口
  • 云服务器监听多个端口
  • 数据包直接转发，不做应用层解析

Application Gateway（应用网关）- FN Connect 的工作方式

FN Connect 的工作流程：

关键特点：

  • 工作在应用层（HTTP/HTTPS）
  • 只需要一个域名入口（remote-xxx.fnos.net）
  • 深度解析请求，进行身份验证和访问控制
  • 动态生成每个服务的访问 URL
  • 不需要为每个服务开放公网端口

特点：

  • 云服务器监听公网端口
  • 数据包直接转发，不做应用层解析
  • 每个服务需要一个公网端口
  • 缺乏应用层的安全控制

Application Gateway（应用网关）

FN Connect 的工作流程：

特点：

  • 工作在应用层（HTTP/HTTPS）
  • 深度解析请求，进行身份验证和访问控制
  • 动态生成每个容器的访问 URL
  • 不需要为每个服务开放公网端口
  • 更强的安全性，但性能略低

为什么 FN Connect 选择 Application Gateway？

从产品设计角度看，飞牛选择 Application Gateway 架构有几个明显优势：

  1. 安全性更强 ：每个请求都经过身份验证，未登录用户无法访问
  2. 无需端口管理 ：用户不需要关心”哪个端口映射到哪个服务”
  3. 统一入口 ：所有服务通过 remote-xxx.fnos.net 统一访问
  4. 官方生态整合 ：可以无缝对接飞牛相册、文件管理等官方应用

缺点：

  • 不支持自定义域名
  • 缺乏高级安全功能（如 WAF、GeoIP 限制）
  • 性能受限于云端 Gateway 的处理能力
  • 不适合运行复杂的服务（如 AI 推理、数据库等）

FN Connect 的定位

通过实验和分析，我认为 FN Connect 的最佳定位是：

飞牛官方生态的远程访问通道

它适合的场景：

  • ✅ 飞牛相册的远程访问和同步
  • ✅ 文件管理的远程访问
  • ✅ 离线下载任务管理
  • ✅ 媒体服务（Emby/Jellyfin）的远程访问

它不适合的场景：

  • ❌ 复杂的自建服务（AI 推理、数据库等）
  • ❌ 需要自定义域名的服务
  • ❌ 需要 Zero Trust 级别安全控制的服务
  • ❌ 需要 CDN 加速的服务

这正是”存储和计算分离”架构的核心理念：

  • FN Connect 用于飞牛 NAS 的官方生态访问
  • Cloudflare Tunnel 用于 Mac mini 上的自建服务访问

第七章：最终架构设计

经过前面的分析和实验，我确定了最终的家庭 Homelab 架构。

核心设计理念：存储和计算分离

整个架构的核心思想是：

飞牛 NAS 专注于存储，Mac mini M4 专注于计算，Cloudflare 负责互联网入口。

这种分离设计带来以下优势：

  1. 性能最大化 ：每个设备专注于自己擅长的事情
  2. 稳定性提升 ：计算服务的故障不影响存储服务
  3. 扩展性更好 ：可以独立升级计算或存储设备
  4. 维护更简单 ：职责清晰，问题定位容易

双通道设计的优势

我的架构采用了”双通道”设计：

通道一：Cloudflare Tunnel + Zero Trust

  • 用于 Mac mini 上自建服务的对外访问
  • 提供自定义域名、WAF防护、CDN加速
  • 安全性最高，适合 AI 服务、Git 服务等
  • 完全独立于 FN Connect

通道二：FN Connect

  • 用于飞牛 NAS 上官方应用的访问
  • 无需额外配置，开箱即用
  • 适合日常快速访问照片、文件等
  • 完全独立于 Cloudflare Tunnel

为什么需要两个通道？

这两个通道服务于完全不同的场景，互不冲突：

  1. Cloudflare Tunnel：

    • 适合自建服务（OpenWebUI、Gitea 等）
    • 提供自定义域名和高级安全功能
    • 无法访问飞牛官方的”一键访问”功能

  2. FN Connect：

    • 适合飞牛官方应用（相册、文件管理）
    • 提供官方生态的无缝体验
    • 无法提供 Cloudflare 的高级安全特性

核心优势：

  • 两个通道完全独立，一个故障不影响另一个
  • 各自发挥优势，互不干扰
  • 用户可以根据需要选择不同的访问方式

存储和计算分离的价值

通过这个架构，我实现了：

存储层（飞牛 NAS）：

  • 专注于文件存储、照片备份、离线下载
  • 低功耗、高稳定性
  • 通过 FN Connect 提供官方生态访问

计算层（Mac mini M4）：

  • 专注于 Docker 服务、AI 推理、Web 服务
  • 高性能、强扩展性
  • 通过 Cloudflare Tunnel 提供安全的互联网访问

连接层（SMB/NFS）：

  • 实现存储和计算的分离
  • 让计算服务可以访问存储资源
  • 同时保持各自独立性

总结

折腾 Homelab 的过程，本质上是一个不断试错、验证、优化的过程。

通过这一系列实验，我得出了一些重要结论：

关于 FN Connect

FN Connect 本质上是一个 Application Gateway ，而不是传统的端口转发服务。它通过：

  • 云端 Gateway 进行身份验证和 URL 路由
  • 本地 Agent 建立加密隧道
  • Session 管理实现访问控制

这种架构的优势是是是安全性强、配置简单是是，缺点是是是灵活性不足、功能有限是是。

更重要的是，，，FN Connect 的定位应该是飞牛官方生态的访问通道，，，而不是通用服务的对外访问方案。

关于架构设计

一个重要的认知转变是：

NAS 不一定是服务器。

很多人刚接触 Homelab 时，总想着把所有服务都部署到 NAS 上。但随着设备越来越多，我逐渐意识到：

存储和计算，本来就是两件不同的事情。

关于存储和计算分离

这是我这次折腾最大的收获：

存储层（飞牛 NAS）应该做好：

  • 存储服务（文件、照片、备份）
  • 保持稳定性和低功耗
  • 提供可靠的数据保护
  • 通过 FN Connect 提供官方生态访问

计算层（Mac mini M4）应该做好：

  • Docker 容器集群
  • AI 推理服务
  • Web 服务和 Git 服务
  • 通过 Cloudflare Tunnel 提供安全的互联网访问

连接层（SMB/NFS）应该做好：

  • 实现存储和计算的连接
  • 让计算服务可以访问存储资源
  • 同时保持各自的独立性和稳定性

最终架构

于是，我的最终架构变成了：

这个架构的核心是：两个通道完全独立，互不冲突

  • Cloudflare Tunnel 专注于 Mac mini 的自建服务
  • FN Connect 专注于飞牛 NAS 的官方应用
  • SMB/NFS 挂载实现存储和计算的分离

这并不是一套”最正确”的方案，但它是我经过一系列实验、验证和思考之后，得到的一套套套最适合我自己套套的家庭 Homelab 架构。

给读者的建议

如果你也在折腾自己的 Homelab，我的建议是：

  1. 动手实验 ：不要只看网上的教程，自己动手验证
  2. 理解原理 ：搞清楚每个技术的底层原理，而不只是”怎么配置”
  3. 量力而行 ：根据自己的硬件条件和实际需求设计架构
  4. 循序渐进 ：从简单服务开始，逐步增加复杂度
  5. 职责分离 ：存储和计算分离，让每个设备专注于自己擅长的事情
  6. 保持好奇 ：Homelab 的乐趣在于探索，而不是一蹴就而就

希望我的这段折腾经历，能给你一些启发。如果有问题，欢迎交流讨论。
